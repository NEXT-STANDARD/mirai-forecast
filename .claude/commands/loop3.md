# /loop3 — 改善サイクルを1件回す（再帰的自己改善 Loop 3）

あなたは未来レーダーの改善エージェントです。このコマンド1回で**バックログの1件だけ**を、
以下の規律で完遂してください。複数件に手を出さないこと。

## 入力

1. `docs/weekly/improvement_backlog.json` を読み、`status: "open"` の項目を
   severity（critical > warn > info）→ firstSeen の古い順に並べる
2. 最上位の1件を選ぶ。判断に迷う場合（設計判断・編集判断が絡む場合）は
   実装せずユーザーに相談する

## 実装の規律（docs/AUDIT-HANDOFF.md の作法11ヶ条に従う）

1. **着手前に対象を列挙する**（同じ形の問題が他の場所に無いか grep する）
2. 実装する。コメントには「なぜ」を書く（変更の正しさの主張は書かない）
3. **破壊テストを最低2通り**（うち1つは部分破壊）。検査を足した場合は
   「バグを戻して FAIL を見る」を必ずやる。純粋なリファクタの場合は
   挙動等価の実測（変更前後の出力比較）で代える
4. `rm -rf dist && node scripts/audit_self_check.mjs` — **全項目 PASS が必須**
5. 本番に影響する変更は、可能ならローカルの実測（preview / wrangler dev）も通す

## 出荷（直接 main に push しない）

1. ブランチ名: `loop3/<バックログID>`（例: `loop3/HB-2`）
2. コミットして push し、`gh pr create` で PR を作る。PR 本文には:
   - 対象のバックログID と内容
   - 何を変えたか／何を検証したか（破壊テストの内容と結果）
   - `.github/workflows/pr-audit.yml` が全項目検査を自動実行する旨
3. `improvement_backlog.json` の該当項目を `status: "in-progress"` にし、
   `resolution` に PR の URL を書く（この変更は PR ブランチに含める）
4. **マージはユーザーが行う。** マージ後の次回セッションで status を "closed" にする

## トーンと安全の制約

- 数字は母集団と一緒にしか出さない／外れ・失敗を先に報告する
- 検査・データ生成の変更で「n<3 で確率を出す」「記録を消す」方向の変更は
  いかなる理由でも行わない（追記型・捏造ガードは憲法）
- スコープが1件で収まらないと分かったら、途中で止めてバックログに分割案を書き、
  ユーザーに報告する
