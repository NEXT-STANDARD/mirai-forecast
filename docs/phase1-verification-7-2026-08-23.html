クランプの副作用

破壊テスト：オッズ辞書を空にし、Polymarket API を不達にする

プリレンダーはビルド時に Polymarket API を直接叩きます（辞書＋ライブ取得の二段構え）。 そこで両方を止めました。API のホスト名を到達不能なアドレスに差し替えています。

オッズ辞書 : 0エントリ Polymarket API : 不達 ──────────────────────────────── 【世界の確率】を持つ銘柄 : 0 / 129 【日本世論調査】 : 129 / 129 自己検証 : 合格 20件 ｜ 不合格 0件 ← PASS

サイトの中心的な比較が全ページから消えても、エンジンは何も言いません。 observedProbs.length が 0 になるので、>= 20 の前提条件を満たさず、判定に入らないためです。

これは仮定の話ではありません。プリレンダーはビルド時にネットワークへ出ます。 Cloudflare のビルドが Polymarket の障害中に走れば、この状態が本番になります。

修正案：件数を「前提条件」ではなく「要件」にする。

例：activeEvents.length >= 40 && observedProbs.length < 20 なら FAIL。

併せて、ライブ取得が0件だったらビルドを失敗させる（黙って続けない）。

所感

N-30 の直し方は、方向として正しいです。

前 : 値が無い → 50% と書く （静かに嘘をつく） 後 : 値が無い → 「該当なし」と書く （無いと言う）

第6回で「値が無いときに、それらしい値を出さない」と書いた原則が、そのまま実装されています。 バッジの重なりも二重空白も片づいていて、細部の処理も丁寧でした。

ただ、同じ原則をあと3か所に適用する必要があります。

OGP・JSON-LD : 直った ← 今回 アプリ本体 : 50% のまま ← N-32（人が見る画面） 出所の表記 : 「独自調査」 ← N-33（無いのは調査ではなくオッズ） 代表値の選び方 : markets[0] ← N-34（多肢イベントで意味が壊れる） 検査 : 全滅でPASS ← Check #14

とくに Check #14 は考えさせられました。 前回の症状（全部50%）を検知する形になっていますが、同じ原因の別の症状（全部消える）は通ります。 再発防止のテストは、症状ではなく原因に紐づけないと次を取り逃がすという例です。 「50%固定でないこと」ではなく「世界オッズが十分な件数で存在すること」を要件にすれば、 どちらの症状も同じ1本で止まります。

そして N-34 は、私が第6回で「実オッズを保存すれば直る」と書いたときに 見落としていた前提でもあります。「実オッズ」と一言で書きましたが、 1イベントに89件のサブマーケットがある世界では、どれを実オッズと呼ぶかが設計判断でした。 そこまで書いていれば、markets[0] は選ばれなかったかもしれません。
