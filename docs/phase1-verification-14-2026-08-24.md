## ❌ N-53 — 機械可読な面だけが嘘をついていた

第11回に og:title、第13回に OGP画像とアプリを直しました。それでも残っていました。

```
Tagger  JSON-LD: name='世界オッズ(YES)' value=0   ← 実際は Lilli Tagger が 0%
Rams    JSON-LD: name='世界オッズ(YES)' value=14  ← 実際は本命 Rams が 14%
静的シェル: 世界のリアルマネー（YES） = 0%        ← 同上
```

**AI連携を掲げている以上、人が読む面より機械が読む面のほうが重い**と考えています。
そこだけが古い枠組みのまま残っていました。

### 原因は「同じ判断を3か所で別々に書いていた」

```
og:title / description : ブロック内で subject を計算
JSON-LD                : "世界オッズ(YES)" を直書き
静的シェル             : isLeaderTop で別途分岐（本命型だけ対応、主語型は素通り）
```

1銘柄につき1回だけ決める `probSubjectLabel` に巻き上げ、4面すべてがこれを使うようにしました。

### Check #30 — 正解を知らない検査

```
og:title   : 【世界の確率「Lilli Tagger」0%】…
description: 世界のリアルマネーは「Lilli Tagger」に 0%。…
静的シェル : 世界のリアルマネー（Lilli Tagger）
JSON-LD    : 世界オッズ(Lilli Tagger)
```

この検査は**「正しい主語」を知りません**。4面が食い違っていないかだけを見ます。
正解を持たないぶん実装から独立していて、**どの面を直し忘れても落ちます**。
これがあれば N-51 も N-53 も初回で捕まえられました。

| 破壊テスト | 結果 |
|---|---|
| JSON-LDだけ固定「YES」に戻す | **5件**が「面ごとに主語が違う」で FAIL |
| 静的シェルのラベルを消す | **37件**が「読み取れません」で FAIL |

## ⚠️ N-54 — 投票が何度でもできる

**表示のバグではありません。** サイトの売りである「日本の世論」そのものの信頼性の問題です。

### 3通りの測り方で裏を取りました

```
スキーマ : japan_vote_logs の列は id, event_id, voted_at, choice,
           region_code, device_type, referrer
           → 利用者を識別する列が1つも無い＝重複を後から取り除けない

実データ : 全48件中、5秒以内の連続投票が1組（2.2秒差の YES→YES、同一銘柄）

本番UI   : 32銘柄を「投票済み」にしても disabled は 0個 / 総ボタン 64個
```

48件のうち1件が既に汚れていました。**n≥3 ガードは3回クリックすれば満たせます。**

### 直したところ（クライアント側・デプロイ済み）

```
handleVote の絞り込みガード   投票ボタンは6コンポーネントから呼ばれる。
                              各所ではなく唯一の絞り込み点で止める
ボタンの disabled             投票済みなら押せない（本番で66個すべて確認）
voter_key の送信              sha256(localStorage の UUID + ':' + 銘柄ID)
```

**種をそのまま送ると1人の投票が銘柄をまたいで紐づきます。** 世論を扱う以上それは避けたいので、
銘柄ごとにハッシュしています。DBは「同じ銘柄に同じキーが二度来た」ことは判定できますが、
**別の銘柄の投票が同じ人物のものかは判定できません**。

### 順序に依存しないようにした

いちばん怖いのは投票そのものを壊すことです。本番DBに対して実測しました。

```
voter_key 付きで送信 → PGRST204 → フォールバック判定 true → 投票が記録された
検証行を削除 → 総数 48件に復帰
```

エラーコードは推測せず実測しました。想定していたメッセージ文言
（`column ... does not exist`）とは違い、実際は
`Could not find the 'voter_key' column of 'japan_vote_logs' in the schema cache` だったので、
判定を実測に合わせて直しています。

### ついでに見つかった既存の防御

```
23503 violates foreign key constraint "japan_vote_logs_event_id_fkey"
```

`event_id` に外部キーが張られていて、**存在しない銘柄には投票できません**。
知らなかった防御が既にありました。

### Check #31 — コードではなくデータを見る

ソースにガードが書いてあるかではなく、**実データに重複が出ていないか**を見ます。
「1人1票」はコードの形ではなくデータの性質なので、データ側で測るべきだと考えました。

母集団は `voter_key` を持つ行だけです。DDL適用前の既存行は
そもそも同一人物か判定できないので入れません。
**日付ではなくデータで絞る**ので、時間が経っても壊れません（N-52 で固定slug一覧が腐った反省）。

検査を書いた時点ではまだ列が無く本物の重複を作れなかったため、
既存48件に対して検出経路を通しました（列の追加後は上記の一意制約が本物の重複を防ぎます）。

| 破壊テスト | 結果 |
|---|---|
| 連打検出の母集団を全行に拡大 | 既知の**2.2秒差1組**を検出 |
| 重複判定を(銘柄,選択)に緩める | **13組**を検出 |

### DDL 適用後の実測（同日中にユーザーが実行）

`scripts/patch_n54_voter_key.sql` 適用後、本番DBに対して4経路すべてを確かめました。
検証行は削除し、件数は元に戻しています（49 → 52 → 49）。

| 経路 | 結果 |
|---|---|
| 本来の経路（列あり・voter_key 付き） | ✅ 1回目で直接成功。フォールバックは走らない |
| **同一銘柄に同一キーで2回目** | ✅ `23505` で弾かれる → クライアントが正常系として無視 |
| 別キー | ✅ 通る（正当な別人を塞がない） |
| キー無し（旧バンドルのキャッシュ） | ✅ 通る（部分インデックスが NULL を除外） |

既存行も無傷です。適用の前後で `voter_key` が NULL の行は一度も弾かれていません。

### 限界（正直に）

**localStorage を消せば別人として投票できます。** これは連打と気まぐれな二重投票を
止めるもので、本気の攻撃者は止まりません。本当に固めるなら IPハッシュや Turnstile が
要りますが、総投票48件という現在の規模には過剰だと判断しました。
規模が変わったら見直す判断です。

## 別セッションとの並行作業について

作業中、別のエージェントが同じツリーにコミットしていました。**衝突はしていません**
（マージコミット0件・衝突マーカーなし・私のコミットは祖先として無事）。

起きたのは、**私の未コミットの編集が向こうの `git add -A` に巻き込まれた**ことです。
ただし奪われたのではなく、読んで直してから取り込まれていました。

```js
// 私が書いたもの
if (userVotes[eventId]) return;

// 実際に入ったもの
if (userVotes[eventId] || votedGuardRef.current[eventId]) return;
votedGuardRef.current[eventId] = true;
```

**向こうの方が正しいです。** 私は絞り込み点に置いたことで満足して、
React の状態更新が非同期であること——同一レンダー内の連打は両方とも古い `userVotes` を
見て通り抜けること——を見落としていました。

残る問題は衝突ではなく**履歴**です。この変更が入ったコミットのメッセージは
`style: widen AboutPage layout…` で、投票ガードにも OGPマニフェストにも sitemap にも触れていません。
後で「いつ連打を塞いだのか」を探す人は、まず見つけられません。
