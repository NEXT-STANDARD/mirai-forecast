## ❌ N-57 — 同じクエリが1回の読み込みで3回

本番のネットワークを発火時刻つきで測ったところ、これが出ました。

```
japan_vote_logs?select=id,event_id,choice
  216ms / 358ms / 560ms      ← 350ms以内に3回
  30225ms / 30506ms          ← 次の周期でも2回
```

原因は `LiveTape` の `useEffect(..., [events])` でした。
**`events` は配列propなので、中身が同じでも参照が変わるたびに再取得が走ります。**
読み込み時に `events` は3回入れ替わります（初期値 → Supabase → Polymarket反映）。

30秒ごとの更新でも同じことが起きるので、**タブを開いている限り無駄が積み上がります。**

### 直し方：取得と表示を分ける

```
取得  useEffect(..., [])  ＋ 30秒間隔（本体と同じく非表示時は休止）
表示  useMemo で voteLogs と events から導出（取得は伴わない）
```

依存配列を `[]` にするだけだと、**歩み値が二度と更新されなくなります**
（従来は「偶然の再取得」で更新されていた）。「リアルタイム歩み値」を名乗る以上、
偶然に頼らず**意図した間隔**に置き換えました。

### 実測

```
修正前: 216, 358, 560ms（3回） → 30225, 30506（2回）
修正後: 685ms → 30620 → 60620  （30秒ごとに1回）
本番反映後の確認: 7秒時点で 1回
```

## ❌ N-58 — 共有カードとリンク先で数字が違う

**この1件は、第14回で追加した Check #29 が自分で見つけました。**

```
❌ bitcoin-up-or-down-on-august-24-2026:
   画像は subject 66% (Up) を描いたが og:title は「【世界の確率「Up」64%】…」
```

枠組み（主語）は一致していて、**値だけが2ポイントずれています**。原因はビルドの順序でした。

```
generate_market_ogp.mjs   ← ここで Polymarket を取得（時刻 T1）
tsc -b && vite build      ← 20〜30秒かかる
prerender_markets.mjs     ← ここでもう一度取得（時刻 T2）
```

**両方が別々に取りに行っていた**ので、その間に価格が動くと食い違います。
値動きの速い銘柄ほど開きます。共有カードを見た人が、リンク先で違う数字を見ることになります。

### 直し方：1回だけ取得して共有する

OGP生成が解決したオッズを `.build-cache/odds-snapshot.json` に書き出し、
プリレンダーが**10分以内のものを再利用**します。無い・古い場合は従来どおり自前で取得します。

```
📸 オッズのスナップショットを保存しました（1608件 / N-58）
📸 OGP生成のオッズを再利用しました（1608件 / 生成から20秒 / N-58）
```

**20秒** — まさにここで価格が動いていた窓です。
「0エントリならビルドを止める」ガードはそのまま残しています。

静的HTMLは7ページすべてに h1 を持っています（N-49 で入れたもの）。

| ページ | ハイドレーション後の h1 | 判定 |
|---|---|:--:|
| `/` | **なし**（最初の見出しが H2） | ❌ |

`/forecast` の `<title>` は「サイバー予報士プロファイル ＆ 全国ランキング」です。
**h1 がページの主題ではなく、訪問者自身の称号になっています。** 無いより悪い状態です。

そして**私の Check #28 は静的HTMLの h1 しか見ていないので、これを通していました。**
また同じ型です。

### 途中で1件、誤検出を出しました

最初の計測では `/letter-to-mike` も「h1なし」と出ました。

報告前に測り直したので外に出していませんが、**速い計測は「無い」と「まだ来ていない」を

## 所感

今回は**測る対象を変えたら別の種類の欠陥が出てきた**という回でした。

15ラウンド、ずっと「表示が正しいか」を見てきました。
速度を測りにいったら、出てきたのは**無駄**（同じクエリ3回）と**食い違い**（ビルド内の時差）で、
どちらも画面を見ているだけでは絶対に気づきません。
N-54 をスキーマから見つけたときと同じで、**見る面を変えると出るものが変わります**。

N-58 については、**自分で追加した検査が自分で見つけた**のが収穫でした。
Check #29 は第14回に「OGP画像とHTMLが食い違わないか」だけを見る検査として入れたもので、
そのとき想定していたのは主語の枠組みのずれでした。
実際に捕まえたのは**ビルド順序に起因する値のずれ**で、想定していなかった原因です。
**正解を持たない検査は、想定していなかった原因も捕まえます。**

一方で、また同じ失敗もしました。N-59 は Check #28 が静的HTMLしか見ていなかったために
素通りしていたものです。第14回・第15回と「面を取りこぼす」型を繰り返していて、
今回もまた1つ。**「どの面を見ているか」を検査自身に書かせる**ような仕組みがないと、
この型は止まらない気がしています。次ラウンドで考えます。
