## ❌ N-38（新規）答えが出せるのに「観測銘柄」にしている9件

【世界観測銘柄】が 8件 → **18件**に増えました。内訳を実測しました。

```
【世界観測銘柄】18件
  シード銘柄（Polymarket に存在せず API 404）        :  8件  ← 抑制が妥当
  真のレンジ型（対応する選択肢が無い）                :  1件  ← 抑制が妥当
  title_en が指す選択肢がサブマーケットに実在する      :  9件  ← 数字を出せる
```

**`title_en` の末尾が、そのまま対象の選択肢になっています。**

| 日本語タイトル | `title_en` の末尾 | 実在するサブマーケット |
|---|---|---:|
| イーサリアムは8月中に3,000ドルに到達するか？ | `↑ 3,000` | **6%** |
| ビットコインは2026年に60,000ドルに到達するか？ | `↓ 60,000` | **100%** |
| イーサリアムは8月17〜23日に2,600ドルに到達するか？ | `↑ 2,600` | **3%** |
| ビットコインは8月17〜23日に78,000ドルに到達するか？ | `↑ 78,000` | **100%** |
| イーロン・マスクのポスト数：…「18回未満」となるか？ | `<20` | **0%** |

`title_en` は `"What price will Ethereum hit in August?: ↑ 3,000?"` という形で、
**コロンの後ろに対象の選択肢がそのまま入っています**。曖昧一致は要りません。

```js
const want = (titleEn || '').split(':').pop().trim().replace(/\?$/, '');   // "↑ 3,000"
const hit  = markets.find(m => (m.groupItemTitle || '').trim() === want);
```

**前回は「任意の選択肢を出していた」、今回は「答えがあるのに出していない」。**
振り子が逆に振れた形です。9件は数字を出せます。

> ついでに気づいた点：`「18回未満」` の英語は `<20` でした（18 ≠ 20）。
> 翻訳時に丸めたと思われますが、閾値は問いそのものなので合わせたほうがよいです。

## ⚠️ Check #19（プレースホルダ検査）の構造的な限界

**破壊テストには合格します。** 辞書に `leaderName: "C"` を注入したところ、3つのメッセージで検知しました。

そのうえで、2つの限界があります。

### ① 判定に、検査対象の関数そのものを使っています

```js
import { isDummyCandidate } from "./resolvePolymarketOdds.mjs";
…
if (val.leaderName && isDummyCandidate(val.leaderName)) { … FAIL … }
```

`isDummyCandidate` が壊れると、**検査も同時に盲目になります**。
実際に `isDummyCandidate` を常に `false` を返すよう壊してビルドしたところ、
EWC の出力は 68% → **61%** に変わったのに、**検査は通りました**。

```
破壊内容 : isDummyCandidate を常に false に
出力     : 【世界本命 68%】 → 【世界本命 61%】（＝除外が効いていない）
自己検証 : プレースホルダ検査は PASS のまま
```

**オラクル（正解の判定役）は、被験者から独立している必要があります。**
インラインで `/^[A-Z]$/` などを持つか、除外リストを検査側にも別途持つのが安全です。

### ② 見ているのは「コミット済みの辞書」で、ビルド出力ではありません

`public/data/market_odds.json` を読んでいます。この辞書を作るのは**同期スクリプト**なので、
リゾルバを壊しても**同期が走るまで辞書は変わらず、検査は気づきません**。
上の破壊テストで検査が通ったのは、これも理由です。

### ③ slug が直書きです

```js
const ewcSlug = "ewc-2026-cs2-winner-20260810160005076";
const wtiSlug = "what-price-will-wti-hit-in-august-2026";
if (oddsDict[ewcSlug]) { … }   // 辞書から消えたら、この検査は黙って何もしない
```

EWC は出来高上位500から外れれば辞書から消えます。そのとき検査1と2は**無言で無効化**され、
残るのは①の循環した全走査だけになります。

> **提案**：`dist/market/*.html` を走査して
> 「`【世界本命 …%】` の銘柄で、leaderName が1文字・`Other`・`Team [A-Z]` でないこと」を
> 検査側の独立した判定で見る。銘柄名を直書きしない。

## 所感

**N-37 の解き方が、私の提案より良かったです。**

私は「410 で消す」か「結果ページとして残す」の二択で書きましたが、
実際には **noindex, follow をつけた結果ページ**という組み合わせでした。
消さずに残し、検索には出さず、内部リンクの流れは保つ。三つとも満たしています。

N-34 も、エムバペを 7% のまま維持したのが良い判断でした。
「本命を出す」を機械的に適用すればケイン 62% になっていたはずで、
**問いが特定候補を名指ししているときは、その候補の確率が答え**という原則が守られています。

一方 N-38 は、**振り子が逆に振れた**形です。

```
第7回 : 任意の選択肢の数字を出していた（出しすぎ）
第10回 : 答えがあるのに出さない（出さなすぎ）
```

どちらも「対象の選択肢をどう特定するか」が決まっていないことから来ています。
そして今回わかったのは、**その答えは `title_en` にすでに書いてある**ということでした
（`… ?: ↑ 3,000?` のコロン以降）。曖昧一致を賢くする必要はなく、**既にある鍵を使えばいい**。

Check #19 については、もう少し重く受け止めています。
**検査が、検査対象の関数を借りて判定していました。**
これは「テストが実装をimportして期待値を作る」のと同じ構造で、
実装が間違った方向に変わると、テストも一緒に間違った方向へ動きます。
破壊テストを1種類（辞書を汚す）だけ試していれば合格に見え、
**関数そのものを壊す**という別の壊し方で初めて露見しました。

破壊テストは「壊し方を変えると別の結論が出る」——
これは第4回の「症状ではなく原因に紐づける」の続きにある教訓だと思います。
次から、新しい検査には**最低2通りの壊し方**（データを壊す／ロジックを壊す）を当てます。
