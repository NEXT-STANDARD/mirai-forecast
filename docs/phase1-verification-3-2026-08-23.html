❌ N-22（新規・重大）ヘッダー是正が、更新ボタンを画面外に追い出しました

症状

修正後のビルドを7つの幅で実測しました。375px で更新ボタンが1ピクセルも見えません。

375px は、いま最も多いスマートフォンの幅です。

到達できません

更新ボタンの位置 : L=386 / R=418 （viewport = 375） body の overflow-x : clip → ページを横スクロールできない .header-inner-slim : clientWidth 375 / scrollWidth 424 / overflow-x: visible → ヘッダー内でもスクロールできない scrollIntoView() : L=386 のまま動かない キーボードフォーカス : ✅ 当たる（document.activeElement になる）

フォーカスは当たるのに、永久に見えない。 WCAG 2.4.11（Focus Not Obscured）に触れます。

原因

f1a7cf1 以前、.header-right-slim にはCSS定義が存在しませんでした。 そのため display: block として折り返し、見た目は崩れる代わりにはみ出しはゼロでした。

今回そこに定義が入りました。

.header-right-slim, .header-right-cluster { display: flex; flex-shrink: 0; /* 縮まない */ flex-wrap: nowrap; /* 折り返さない */ }

見た目は整いましたが、縮みも折り返しもしない一列になりました。

そして決定打がこれです。モバイル救済のメディアクエリが、旧クラス名しか見ていません。

@media (max-width: 360px) { /* ← はみ出しは 414px から始まっている */ .header-main-bar { … } /* ← 新しい .header-inner-slim には当たらない */ .header-left-cluster { … } /* ← 新しい .header-left-slim には当たらない */ .header-right-cluster { … } /* ← 新しい .header-right-slim には当たらない */ }

f1a7cf1 は基本ルールには別名を足しました（.header-inner-slim, .header-main-bar { … }）が、 メディアクエリの中には足していません。だから狭い画面での救済が丸ごと不発です。

360px でだけ少しマシなのは、ボタン単体のルール（.btn-header-*）はクラス名が変わっておらず、 そこだけ効いているからです。375px が 360px より悪いのは、そのためです。

修正案（実測で確認済み）

メディアクエリに新クラス名を足し、境界を実際にはみ出しが始まる幅まで上げます。

@media (max-width: 440px) { /* 360 → 440 */ .header-inner-slim, .header-main-bar { … } .header-left-slim, .header-left-cluster { … } .header-left-slim h1, .header-left-cluster h1 { … } .header-right-slim, .header-right-cluster { … } }

❌ N-23（新規・重大）_redirects は1行も有効になっていません

Cloudflare 自身のパーサで実測しました

wrangler pages dev（Cloudflare Pages と同じ _redirects パーサ）に、実際のビルド成果物を読ませました。

✨ Parsed 0 valid redirect rules. ▲ WARNING Found 2 invalid redirect rules: at dist/_redirects:4 | /ogp/* 404 at dist/_redirects:5 | /assets/* 404

有効ルールは0件。 記法が [source] [destination] [code?] の3トークンで、 404 は宛先として解釈できず、かつ _redirects がサポートする status は 301/302/303/307/308 のみです。 _redirects から 404 を返す方法はありません。

同じサーバで挙動も測りました。本番とまったく同じです。

実在OGP : 200 / image/png ← 変化なし 不在OGP : 200 / text/html (5261 bytes) ← 直したはずの症状がそのまま 不在assets : 200 / text/html

「記法を直す」と、今度は125枚のOGPが全部壊れます

正しい3トークン記法に直したらどうなるかも実測しました。

_redirects: /ogp/* /ogp-placeholder.png 302 ──────────────────────────────────────────── 実在OGP : 302 → /ogp-placeholder.png ← 実在する画像まで奪われる 不在OGP : 302 → /ogp-placeholder.png

Cloudflare の仕様どおりでした。リダイレクトは実在アセットより優先されます。 つまり /ogp/* にワイルドカードのリダイレクトを置いた瞬間、P0-5 で作った125枚が全滅します。

いま無効であることが、たまたま事故を防いでいる状態です。 この2行は「直す」のではなく、消すのが正解です。

代替案（実測済み・ただし副作用あり）

dist/404.html を置くと、Cloudflare Pages は SPA フォールバックの代わりにそれを404で返します。 中身を index.html のコピーにすると、こうなりました。

所感

今回は、報告と実測が最も大きく食い違った回でした。

ただ、食い違いの中身は「嘘」ではありません。3件ともやったことは正しく報告されています。

「クラス定義を配備した」 → 事実。配備されている 「_redirects に404を定義した」 → 事実。ファイルに書いてある 「Deploy Hook を配備した」 → 事実。ステップは存在する

ズレているのは、やったことと、効いたことの間です。

  • 定義は配備されたが、メディアクエリには配備されていなかった
  • 404は書かれたが、Cloudflareがその記法を受け付けない
  • ステップは配備されたが、Secretが無いので実行されない

3件とも「ファイルに書いた」で検証が止まっています。 そして Check #18 も、まさに「ファイルに書いてあるか」を見る検査です。 検査が、報告と同じ場所で止まっている。 だから20/20で通ります。

第14回から一貫して申し上げてきたことですが、今回はそれが最も鮮明でした。 書いたことの確認と、効いたことの確認は、別の作業です。

_redirects については、こちらも学びがありました。 私は当初「記法が2トークンで不正だから直すべき」と考えましたが、 実際に Cloudflare のパーサに読ませ、さらに「正しい記法」を試したところ、 正しい記法のほうが遥かに危険でした（125枚のOGPが全滅する）。 仕様を読んで直すのではなく、動かして確かめてよかったと思います。

N-22 についても、指摘だけで終わらせず修正案を実際にビルドして7幅で測りました。 「440pxに上げれば直るはず」ではなく、「320〜768pxで更新ボタンが100%見える」という 実測値をお渡しできます。指摘の質は、その指摘を自分で検証できるかで決まると考えています。
