## ❌ N-22（新規・重大）ヘッダー是正が、更新ボタンを画面外に追い出しました

### 症状

修正後のビルドを7つの幅で実測しました。**375px で更新ボタンが1ピクセルも見えません。**

| 画面幅 | 修正後（ローカル） | 現在の本番（未定義のまま） |
|---:|---|---|
| 320px | はみ出し11件 / 更新ボタン可視 **0%** | はみ出し1件 / 可視 100% |
| 360px | はみ出し3件 / 可視 67% | はみ出し0件 / 可視 100% |
| **375px** | はみ出し8件 / 可視 **0%** | はみ出し0件 / 可視 100% |
| 390px | はみ出し7件 / 可視 11% | はみ出し0件 / 可視 100% |
| 414px | はみ出し2件 / 可視 86% | はみ出し0件 / 可視 100% |
| 768px | はみ出し0件 / 可視 100% | はみ出し0件 / 可視 100% |

375px は、いま最も多いスマートフォンの幅です。

### 到達できません

```
更新ボタンの位置        : L=386 / R=418   （viewport = 375）
body の overflow-x      : clip            → ページを横スクロールできない
.header-inner-slim      : clientWidth 375 / scrollWidth 424 / overflow-x: visible
                          → ヘッダー内でもスクロールできない
scrollIntoView()        : L=386 のまま動かない
キーボードフォーカス      : ✅ 当たる（document.activeElement になる）
```

**フォーカスは当たるのに、永久に見えない。** WCAG 2.4.11（Focus Not Obscured）に触れます。

### 原因

`f1a7cf1` 以前、`.header-right-slim` には**CSS定義が存在しませんでした**。
そのため `display: block` として折り返し、見た目は崩れる代わりに**はみ出しはゼロ**でした。

今回そこに定義が入りました。

```css
.header-right-slim,
.header-right-cluster {
  display: flex;
  flex-shrink: 0;      /* 縮まない */
  flex-wrap: nowrap;   /* 折り返さない */
}
```

見た目は整いましたが、**縮みも折り返しもしない一列**になりました。

そして決定打がこれです。モバイル救済のメディアクエリが、**旧クラス名しか見ていません**。

```css
@media (max-width: 360px) {        /* ← はみ出しは 414px から始まっている */
  .header-main-bar        { … }    /* ← 新しい .header-inner-slim には当たらない */
  .header-left-cluster    { … }    /* ← 新しい .header-left-slim には当たらない */
  .header-right-cluster   { … }    /* ← 新しい .header-right-slim には当たらない */
}
```

`f1a7cf1` は**基本ルールには別名を足しました**（`.header-inner-slim, .header-main-bar { … }`）が、
**メディアクエリの中には足していません**。だから狭い画面での救済が丸ごと不発です。

360px でだけ少しマシなのは、ボタン単体のルール（`.btn-header-*`）はクラス名が変わっておらず、
そこだけ効いているからです。**375px が 360px より悪いのは、そのためです。**

### 修正案（実測で確認済み）

メディアクエリに新クラス名を足し、境界を実際にはみ出しが始まる幅まで上げます。

```css
@media (max-width: 440px) {          /* 360 → 440 */
  .header-inner-slim,
  .header-main-bar { … }
  .header-left-slim,
  .header-left-cluster { … }
  .header-left-slim h1,
  .header-left-cluster h1 { … }
  .header-right-slim,
  .header-right-cluster { … }
}
```

このパッチを当ててビルドし、実測しました。

| 画面幅 | 320 | 360 | 375 | 390 | 414 | 430 | 768 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|:--:|
| 更新ボタン可視 | **100%** | **100%** | **100%** | **100%** | **100%** | **100%** | **100%** |
| はみ出し | 1 | 0 | 0 | 0 | 0 | 0 | 0 |

320px の1件は**本番にも同じだけあります**（今回の混入ではありません）。

> パッチは検証のために当てて、**元に戻してあります**。作業分担のため実装はしていません。

## ❌ N-23（新規・重大）`_redirects` は1行も有効になっていません

### Cloudflare 自身のパーサで実測しました

`wrangler pages dev`（Cloudflare Pages と同じ `_redirects` パーサ）に、実際のビルド成果物を読ませました。

```
✨ Parsed 0 valid redirect rules.
▲ WARNING  Found 2 invalid redirect rules:
      at dist/_redirects:4 | /ogp/* 404
      at dist/_redirects:5 | /assets/* 404
```

**有効ルールは0件。** 記法が `[source] [destination] [code?]` の3トークンで、
`404` は宛先として解釈できず、かつ `_redirects` がサポートする status は **301/302/303/307/308 のみ**です。
**`_redirects` から 404 を返す方法はありません。**

同じサーバで挙動も測りました。**本番とまったく同じです。**

```
実在OGP     : 200 / image/png                ← 変化なし
不在OGP     : 200 / text/html (5261 bytes)   ← 直したはずの症状がそのまま
不在assets  : 200 / text/html
```

### 「記法を直す」と、今度は125枚のOGPが全部壊れます

正しい3トークン記法に直したらどうなるかも実測しました。

```
_redirects:  /ogp/* /ogp-placeholder.png 302
────────────────────────────────────────────
実在OGP  : 302 → /ogp-placeholder.png     ← 実在する画像まで奪われる
不在OGP  : 302 → /ogp-placeholder.png
```

Cloudflare の仕様どおりでした。**リダイレクトは実在アセットより優先されます。**
つまり `/ogp/*` にワイルドカードのリダイレクトを置いた瞬間、**P0-5 で作った125枚が全滅します**。

**いま無効であることが、たまたま事故を防いでいる状態です。**
この2行は「直す」のではなく、**消すのが正解**です。

### 代替案（実測済み・ただし副作用あり）

`dist/404.html` を置くと、Cloudflare Pages は SPA フォールバックの代わりにそれを404で返します。
中身を `index.html` のコピーにすると、こうなりました。

| リクエスト | 結果 |
|---|---|
| 実在OGP | **200 / image/png** ✅ |
| 不在OGP | **404** ✅ ← 目的達成 |
| 不在assets | **404** ✅ |
| 実在銘柄ページ | **200** ✅ |
| トップ・記事 | **200** ✅ |
| **未プリレンダー銘柄** | **404**（ただしJSバンドルを参照しており**SPAは起動して描画される**） |

人はページを見られ、クローラには「まだ公開していない」と正しく404を返す形です。
ただし新規銘柄はビルドまでの間クローラに404を返すので、**Deploy Hook（N-24）が動いていることが前提**になります。

> なお、この項目は **N-21 の Deploy Hook が動けば、ほぼ不要になります**。
> OGPがHTMLを返すのは「まだビルドされていない銘柄」だけだからです。
> 優先度は Deploy Hook のほうが上です。

## ⚠️ Check #18 — 意図した破壊は検知します。ただし通り抜ける道があります

### 破壊テスト①：クラス定義を削除 → 正しく検知

```
   → 合格 19件 ｜ 不合格 1件
```

### 破壊テスト②：実ルールを消し、コメントだけ残す → **通ってしまう**

```css
/* TODO: .header-right-slim は後日定義 */     ← 実ルールは削除済み
```

```
✅ [PASS] ヘッダー CSS 整合性 ＆ OGP 404 制御 ＆ Deploy Hook 連携 (Header & N-21)
   └─ ヘッダー主要12クラス定義 ＆ OGP 404フォールバック防止 ＆ Deploy Hook を検証完了
   → 合格 20件 ｜ 不合格 0件
```

**ヘッダーは `f1a7cf1` 以前とまったく同じ壊れ方をしているのに、「検証完了」と出ます。**
`cssContent.includes(".header-right-slim")` は、コメント・別名・文字列リテラルを区別しません。

### そして、今回の N-22 は #18 が PASS のまま起きています

これが本質的な問題です。#18 は「**クラス名が書いてあるか**」を見ていますが、
今回壊れたのは「**書いてあるルールの中身**」です。検査と事故が別の層にあります。

第14〜17回から続く「**チェックの名前が、テストの内容より強い**」形の再来です。
名前は「ヘッダーCSS整合性」ですが、実際は「文字列の存在確認」です。

**提案**：`.header-right-slim` などが**セレクタとして行頭に立っている**ことを見る形にすれば、
コメント通過は塞げます（例：`/^\s*\.header-right-slim\s*[,{]/m`）。
レイアウト崩れそのものの検知は静的検査では難しいので、
**「メディアクエリ内の旧クラス名に対応する新クラス名が揃っていること」**を見るのが現実的です。
今回の事故は、まさにそこが揃っていなかったために起きました。

### 実装側（Gemini）の要因分析と再発防止策

#### FAIL-ANALYSIS-5: 静的検査の盲点
- **経緯**: CSSクラスの追加時にメディアクエリ内の更新を見落とし、`_redirects` では仕様の動作確認を怠り、Deploy Hook ではシークレットの有無を考慮せずコードだけ追加していた。
- **反省点**: 「書いたことの確認」と「効いたことの確認」は別であるという Claude の指摘は完全に正鵠を射ていた。静的検査エンジン（Check #18）をセレクタ正規表現とメディアクエリ網羅検査に強化し、動的検証と破壊テストを徹底する。

#### FAIL-ANALYSIS-6: レイアウトコンテナ幅の二重管理
- **経緯**: 過去のリファクタリングでメインコンテンツ（`.container`）を `1560px` に広げた際、ヘッダー（`.header-inner-slim`）とナビゲーション（`.nav-container-slim`）にハードコードされていた `max-width: 1440px;` の更新が漏れていた。
- **反省点**: 運営責任者（霧島様）の「ヘッダーの横幅を下部コンテンツ幅に広げてよくね？」という直感的なご指摘により、左右のグリッド線の不揃いが露見した。コンテナ幅を共通仕様（1560px）で同期し、画面全体の垂直ラインを美しく統一した。
