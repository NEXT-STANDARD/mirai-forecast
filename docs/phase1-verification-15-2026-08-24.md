## 🔴 N-56 — 他人のサイトで嘘をついていた

埋め込みウィジェットは、記事に `<iframe>` を1行貼るだけで使えるものです。
**メディア側の信用を借りて表示される面**です。

### 本番で実測した挙動

```
クリック前: 日本の生活者世論 (n=6)  YES 50%   ／ 乖離 50% GAP
クリック後: 日本の生活者世論 (n=6)  YES 52%   ／ 乖離 52% GAP
発生した通信: 0件
```

コードはこうなっていました。

```js
const japanYes = userVote === 'YES'
  ? Math.min(100, item.japanVotes.percentYes + 2)   // クリックすると +2%
  : userVote === 'NO'
  ? Math.max(0, item.japanVotes.percentYes - 2)     // クリックすると -2%
  : item.japanVotes.percentYes;
```

**投票は記録されず、表示だけが読者自身のクリックで ±2% 動きます。**
`n` は 6 のまま据え置きなので、「6人が52%」と表示することになります。
実際には6人は50%と言っていて、7人目（読者）はどこにも記録されていません。
乖離の見出しも、その捏造値から作り直されていました。

`+2` という定数に根拠はありません。

### 直したところ

```
±2% の加算を撤去
submitVoteToSupabase に接続し、戻り値が true のときだけ表示を動かす
動かすときは分子と分母の両方を足す（n も増える）
1銘柄1票のガードと disabled
```

`submitVoteToSupabase` は void を返していたので、**記録できたかどうかを返す**ように変えました。
記録できていないのに数字だけ動かす、という状態を型で作れなくするためです。

### 「サンプル収集中」の解除判定は元の母数で行う

実装中に気づいた点です。表示を実効集計（記録済みの票を含む）から作ると、
**読者自身の1票で「サンプル収集中」が解除されてしまいます**。
n=2 の銘柄で読者が投票すると n=3 になり、その場でパーセンテージが現れる。

数字としては正しいのですが、**「自分のクリックで世論が見えるようになった」という錯覚**は、
いま直している捏造と同じ種類のものです。
表示は実効集計から作り、**解除の判定は元の母数で行う**ようにしました。

### 修正後の実測

```
修正前の挙動: n=6のまま  50% → 52%（+2の定数）  通信 0件
修正後の挙動: n=6 → 7    50% → 57%              通信 1件
```

57% は 3/6 → 4/7 の正しい計算です。`voter_key` が実際に入っていること
（`aaf15ab65471a810…`）も確認しました。N-54 の仕組みが埋め込み経路でも働いています。
検証票は削除し、総数50・対象銘柄 n=6 YES=3 に戻しています。

## ⚠️ 書いた本人が、対象の欠陥を見逃していた

Check #32 の初版はこうでした。

```js
const HARDCODED = /(?<![A-Za-z])(YES|NO)\s*\{[^}]*worldProb(Yes|No)/;
```

同一行に `worldProbYes` があることを要求しています。
ところが**実際の N-55 はこの形ではありませんでした**。

```js
const worldYes = item.worldProbYes;   // ← 別行で別名を付ける
...
YES {worldYes}%                        // ← 別行で直書き
```

**この検査は、それが書かれた原因である欠陥そのものを素通りします。**
別名を追うように直したところ、その場で `OgpPreviewModal`（7面目）が出ました。
広げなければ、いまも残っていたはずです。

| 破壊テスト | 結果 |
|---|---|
| 直接参照の形に戻す | `ForecastHubPage:285` を検出 |
| 別名経由の形に戻す | `EmbedWidgetPage:150` を検出 |

なお破壊テスト中、不合格が2件出ました。2件目は型チェックの
「`positiveLabel` が未使用」でビルドが止まったもので、私の編集の副作用です。
**型チェックが第二の防御線として働いた**形でした。

## 所感

今回の N-56 は、これまで見つけたどの欠陥とも種類が違いました。
表示がずれていたのでも、数字が古かったのでもなく、**数字が存在しなかった**ものです。

しかも出ていた場所が悪い。埋め込みウィジェットは**メディア側の信用を借りて**表示されます。
自分のサイトで間違った数字を出すのと、他人の記事の中で出すのとでは、
訂正のコストがまるで違います。

見つけ方は、前回の反省がそのまま効きました。
「別セッションが作った、誰も検証していない面」を狙う、と決めて入ったので、
**最初に疑ったのが埋め込みの投票挙動**でした。
そして N-11（監査期の「埋め込みが日本世論を固定値で表示」）という前科があったことも、
どこを見るかの手がかりになりました。**同じ場所は二度壊れます。**

もう1つ。今回いちばん堪えたのは、**自分で書いた検査が、その検査を書く原因になった欠陥を
見逃していた**ことです。第11回の Check #19 とまったく同じ構図でした。
あのときの教訓は「新しい検査には最低2通りの壊し方を当てる」でしたが、
今回それを守っていても、当てた2通りが**どちらも同一行の形**だったら見逃していました。

正しくは「**実際に起きた欠陥そのものを、検査に食わせてみる**」です。
`/tmp` に退避してあった修正前のソースを検査にかけて、初めて穴が見えました。
破壊テストは自分で作った壊し方ではなく、**現実に起きた壊れ方**を再現すべきでした。
