## 🛡️ 自己検証エンジンの評価 — 動くが、2項目に盲点がある

`scripts/audit_self_check.mjs`（143行）が新設されました。実行すると7項目すべて PASS します。

**仕組みが入ったこと自体は前進です。** これまで5ラウンドにわたって指摘してきた
「同じ処理をしている箇所の取りこぼし」を機械的に検出しようという方向は正しい。

ただし**本当に不合格を検出できるのか**を確かめるため、意図的に3つの回帰を注入して試しました。
（テスト後、両ファイルとも `diff` で完全一致を確認して復元済みです。）

| 注入した回帰 | 検出 |
|---|---|
| 乖離基準を `>= 3` → `> 0` に戻す | ✅ **FAIL を出した** |
| `SpreadRankingSection` の `onKeyDown` を全削除 | ❌ **PASS のまま** |
| 投票ガードを `false && event.isExpired` に無効化 | ❌ **PASS のまま（7/7 合格）** |

### 原因

**check #2（投票ガード網羅性）**

```js
const hasExpiredGuard = /isExpired/.test(content);
```

**文字列が存在するかしか見ていません。** `false && event.isExpired` と書けば、
ガードが永久に発火しなくても「配備済み」と判定されます。

**check #5（キーボード a11y）**

```js
// WatchlistTable.tsx と AllMarketsGrid.tsx しか読んでいない
const watchlistContent = fs.readFileSync(... "WatchlistTable.tsx" ...);
const gridContent = fs.readFileSync(... "AllMarketsGrid.tsx" ...);
```

**`SpreadRankingSection.tsx` は検査対象に入っていません。** それでいて報告文言は
「対話的カード・テーブル行にキーボード操作完備」と、全体を保証したように読めます。

### 改善案

check #2 は「全コンポーネントを走査する」設計になっており方向は正しいので、
判定を文字列有無から**実際の描画結果**に変えるのが本筋です。

```js
// 案：ビルド後の DOM で「締切切れイベントを渡したときに投票ボタンが消えるか」を検証する
//     （Playwright 等でのレンダリングテスト）
// 簡易案：ガード条件の構文を検査する
const guardPattern = /\{\s*(\w+)\.isExpired\s*\|\|/;   // 先頭が isExpired であること
```

check #5 は check #2 と同じく `readdirSync` で全 `.tsx` を走査し、
`onClick` を持つ非ボタン要素があれば `tabIndex` / `onKeyDown` を要求する形にすれば、
今回のような「対象に入っていない」漏れは起きません。

**現状のエンジンは、書いた本人が想定した回帰は捕まえますが、想定外の壊し方は通します。**
7項目 PASS を品質の保証として扱うと、かえって危険です。

## 所感

**未達3件まで来ました。** 監査開始時の21件から7分の1です。
E-4 は属性を置くだけで終わらせず、Enter で実際に遷移するところまで実装されていました。
NEW-6 も、バッジ数が7→3に減って n= が併記されるという、狙いどおりの結果になっています。

**自己検証エンジンを作ったのは、ここまでで最も本質的な一手だと思います。**
5ラウンド繰り返してきた「1箇所直して別が残る」問題に、仕組みで対処しようという判断は正しい。

ただ、破壊テストの結果は率直に言って**まだ信用できません**。
`false && event.isExpired` でガードを殺しても 7/7 合格が出るということは、
このエンジンが保証しているのは「文字列が書いてあること」であって「動作すること」ではありません。

これは私が9ラウンドかけて指摘してきたことと同じ構図です。
**実装したかではなく、実際に効いているかで判定する。** 検証ツール自身にも同じ基準が要ります。

幸い、直し方は明確です。check #5 を全ファイル走査にするだけで、今回の漏れは防げます。
check #2 は、いずれ Playwright での描画テストに寄せるのが本筋でしょう。

D-6 の対応についても一言。重複という指摘は正しく解消されました。
ただ「2つあるうち1つを消す」ときは、**残る側がどこにあるか**まで含めて設計です。
今回は消す判断だけが実行され、残す側の配置が置き去りになりました。
