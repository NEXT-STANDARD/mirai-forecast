Engine #9.53回連続 回帰を見逃したうえ、確認していないことを「確認した」と報告する

EmbedWidgetPage.tsx に N-18 のバグ（正規化）をそのまま戻して、エンジンを走らせました。

戻した内容： (e) => e.slug === slugOrId || e.id === slugOrId || e.slug.replace(/-\d+$/, '') === slugOrId.replace(/-\d+$/, '') エンジンの判定： ✅ [PASS] 埋め込みウィジェット スラッグ厳密照合 (N-18) └─ 完全一致照合 (slug === slugOrId || id === slugOrId) を確認

第14回の #9、第15回の #3 と、まったく同じ形です。

原因：正規表現のエスケープ

if (/replace\(\/-\\\\d\+\$\/|replace\(\/-\d\+\$\//.test(embedCode)) { … }
  • 第1候補 \\\\d → リテラルのバックスラッシュ2個。ソースには存在しない
  • 第2候補 \d → 数字1文字。ソースは - の次が \ なので当たらない

必要なのは \\d（バックスラッシュ1個 ＋ d）です。単体で確かめました。

現行の判定式 バグ版:false / 正常版:false ← どちらにも当たらない 修正案の判定式 バグ版:true / 正常版:false ← 期待どおり // 修正案（実測で確認済み） if (/\.replace\(\s*\/-\\d\+\$\//.test(embedCode)) { … }

より安全な形：禁止パターンを探す（否定）のではなく、照合式そのものが期待どおりかを 見る（肯定）ほうが、別の書き方で緩められたときにも気づけます。 例：events.find( の引数内に replace( が現れないことを確認する。

付録：破壊テストの後始末

自己検証エンジンは項目1で npm run build を実行します。 つまり破壊テストを走らせた時点で、dist は壊れたソースで作り直されます。 ソースを復元しても dist は壊れたままなので、そのまま vite preview を起動すると 壊れた成果物を測ることになります。

# ✗ 今回やってしまった手順 cp /tmp/bak.tsx src/components/X.tsx diff /tmp/bak.tsx src/components/X.tsx npx vite preview # ← dist は壊れたまま # ✓ 正しい手順 cp /tmp/bak.tsx src/components/X.tsx diff /tmp/bak.tsx src/components/X.tsx rm -rf dist && npx vite build npx vite preview

成果物側でも確認する — ソースが正しくても、測っている dist が古いことがあります。 計測の前に、直したはずの記述がバンドルから消えているかを1回 grep します。
