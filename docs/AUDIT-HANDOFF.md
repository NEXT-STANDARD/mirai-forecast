### ✅ P0-6・本番404 は解決（2026-08-25・D 完了）— ユーザー操作待ちは **0件**

**根因**：このプロジェクトは Pages ではなく **Worker**（`npx wrangler deploy`）として
デプロイされていた（ユーザー提供のビルドログで確定）。リポジトリに wrangler 設定が
無いため、CI の自動セットアップが毎ビルド `not_found_handling: "single-page-application"`
を生成——これがソフト404の正体。Pages 専用の `functions/`・`_routes.json` は
**そもそも読まれない仕組み**で、過去の診断が「設定は正しいのに効かない」で
行き詰まったのは、見ていた設定が別プラットフォームの流儀だったから。
**教訓：プラットフォームの同定を前提にしない。ビルドログが一次資料。**

対応（すべてリポジトリ側で完結・ダッシュボード操作は結局不要だった）：
- `wrangler.jsonc` をコミット（404-page / worker main）→ 自動生成が止まった
- `worker/index.ts` + `worker/mcp.ts`：/api/mcp を実データで実装。
  旧 functions/api/mcp.ts は**ハードコードのダミーデータを返す雛形**だったため全面置換。
  データ源はビルド時生成の `dist/data/mcp_snapshot.json`（掲載銘柄のみ・n<3は確率を出さない）
- 事前に `/embed/*` の静的シェル114件を prerender（フォールバック喪失で配布済み埋め込みが
  全滅する罠を回避）。レガシー functions/ は削除
- 検査39項目め（wrangler設定＋snapshot整合＋n<3捏造ガード）。破壊テストは
  SPA改悪＋捏造14件の二重注入を1検査で両方検知

本番実測（2026-08-25）：/api/mcp 実データJSON（乖離1位=ホルムズ50%GAP）／
未知パス 404＋404.html ／ 全ルート（トップ・銘柄・埋め込み・track-record・guide）200 回帰なし

### ⚙️ 作法（毎ラウンド守ること）

1. 実装と検証を別ターンに分ける
2. 破壊テストは最低2通り。かつ**部分的に**壊して検査の粒度も見る
3. 本番の実測を必ず経由する
4. 検査を足したら、その検査自身の弱点を探す
5. **列挙は人ではなく検査にやらせる**（母集団を固定リストで持たない）
6. **破壊テストには、実際に起きた壊れ方を再現する**
7. ハイドレーション後の計測は待ち時間を十分に取る
8. 母集団を導出する検査には**「新しいファイルを1つ足す」試験**を当てる
9. **grep の件数は候補の数であって欠陥の数ではない**
10. デプロイ確認をバンドルの grep でやらない（遅延チャンク・日本語エスケープで3回誤った）
11. スクリプトに dry-run を足すときは「DBに書くか」ではなく**「何を書くか」**を数える

### 横はみ出しは `scrollWidth` では検出できない

```js
if (r.right > vw + 1 || r.left < -1) {
  let p = e.parentElement, inScroller = false;
  while (p) {
    const o = getComputedStyle(p).overflowX;
    if ((o === 'auto' || o === 'scroll') && p.clientWidth < p.scrollWidth) { inScroller = true; break; }
    p = p.parentElement;
  }
  if (!inScroller) bad.push(e);   // ← クリップされて到達不能
}
```

意図した帯は3つだけです：`category-nav-slim` / `tape-items-scroll` / `hot-keywords-row`。
