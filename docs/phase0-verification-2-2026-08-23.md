## 🔴 N-20（新規・最優先）23銘柄が開けない — 原因は `.limit(100)`

### 対照実験

同じ条件で、**アプリが読み込む上位100件の内と外**を6件ずつ測りました。

| 群 | 詳細ページが表示された数 |
|---|---|
| **圏内**（updated_at 上位100件） | **6 / 6** ✅ |
| **圏外**（101位以降） | **0 / 6** ❌ |

結果が完全に分かれました。**遅延ではありません**（1件を26秒待っても未表示を確認）。

### 原因

```js
// src/services/polymarketService.ts:115
.from('events')
.select('*')
.eq('is_active', true)
.order('updated_at', { ascending: false })
.limit(100);          // ← ここ
```

一方で、Phase 0 が生成しているのは **Supabase の有効銘柄すべて**です。

```

プリレンダーHTML          : 123件（sitemap も123件、OGP画像も123枚）
アプリが読み込む銘柄      : 100件（updated_at 降順）
                            ────────
差分（開けない銘柄）      :  23件
```

**プリレンダーと sitemap が「ある」と宣言している23銘柄を、アプリ本体が知りません。**
`detailMarketId` は解決されるのに、その ID を持つ銘柄が一覧に存在しないため、
トップページにフォールバックします。

### これは放置すると悪化します

銘柄は日々増えています。


### 修正案

**主案：`.limit()` を有効銘柄数に追随させる**

```js
.limit(500)   // または .limit() を外す
```

現状123件なら十分な余裕を持たせるのが素直です。件数が増え続ける設計なので、
固定値を大きめに取るか、`count` を先に取って動的に決めるかのどちらかです。

**併せて：不整合を検知するチェックを追加**

```
Supabase の有効銘柄数 === プリレンダー件数 === アプリが読み込む上限
```

この3つがズレたら FAIL にする。今回のように「生成はしたが到達できない」を防げます。

## ⚠️ 307 リダイレクトは残っています

`.html` 形式とディレクトリ形式の**両方**を出力したため、Cloudflare Pages は
ディレクトリ形式を優先し、リダイレクトが残りました。

```
/market/<slug>        → HTTP 307 → /market/<slug>/
/market/<slug>/       → HTTP 200
/market/<slug>.html   → HTTP 307 → /market/<slug>/
```

宣言と実体の不一致も前回のままです。

| 要素 | 形式 |
|---|---|
| 実際に200を返すURL | `/market/<slug>/` |
| canonical / og:url / sitemap | `/market/<slug>`（スラッシュなし） |

**実害は小さくなりました**（アプリが末尾スラッシュに耐性を持ったため、ユーザー体験は同じ）。
ただし canonical がリダイレクトするURLを指す状態は続いています。

**ディレクトリ形式の出力をやめて `.html` 単独にすれば**、307が消えて宣言と実体が一致します。
両方置いたことが、かえって主案の効果を打ち消しました。

## 🔄 自己訂正：今回も計測ミスが2件ありました

**並列数を上げすぎると、遅延を故障と誤認します。**

### ② 「新チェックは破壊テストを通らない」も誤りでした

最初の破壊テストで PASS が出たため「検知できない」と判定しかけましたが、
**私の文字列置換が実際には効いていませんでした**（Python の `chr()` を使った検算式が
誤っており、置換されていないのに「0件になった」と表示していた）。

grep で消滅を確認してからやり直したところ、**正しく FAIL** しました。

これで私の計測ミスは**9件目**です（oklch未対応／翻訳判定／行番号ずれ／母集団がトップのみ／
破壊テスト後の再ビルド漏れ／n<3のid未取得／OGP破壊テストの対象不一致／今回の2件）。

**傾向がはっきりしています。** 私のミスは全部「**測り方の設定を確認せずに結論を出した**」型です。
並列数、置換の成否、取得したカラム、ビルドの鮮度。今回から、
**否定的な結論を出す前に「測定系が生きているか」を1回確かめる**ことを手順に入れます。
