## ❌ N-33（新規）Polymarket の銘柄を「独自調査銘柄」と呼んでいます

数字を出さない85銘柄には、こう書かれています。

```
og:title : 【日本世論調査】MLB公式戦: Atlanta Braves vs. Milwaukee Brewers 勝敗予測
OGP画像  : 「世界の予測市場 (該当なし)」「独自調査銘柄」「日本世論専用」
バッジ    : 「日本世論独自調査」
```

しかし **MLBのカードは Polymarket 由来です**（`title_en` が Polymarket の原文）。
「該当なし」でも「独自調査」でもありません。**オッズが取れていないだけ**です。

### 85件の内訳を測りました

```
オッズ辞書にある（idで一致）  : 44件
辞書にない                   : 85件
  ├ end_date が null（初期投入の独自銘柄と思われる）: 9件
  └ 残り                                          : 76件 ← Polymarket由来
slug での照合を足しても増えない : 44件のまま
```

### なぜ取れないのか

辞書は **24時間出来高の上位500イベント**から作られています。

```js
// sync_polymarket_cron.mjs / prerender_markets.mjs
`https://gamma-api.polymarket.com/events?limit=100&offset=${0..400}
 &active=true&closed=false&order=volume24hr&ascending=false`
```

`events` テーブルは銘柄を蓄積し続けるので、**上位500から外れた銘柄が残り続けます**。
その結果、**66%の銘柄が「独自調査」を名乗る**状態になっています。

**「日本語で読めるPolymarket」を掲げるサイトで、3分の2が「Polymarketに無い」と言っている**のは、
名乗りと食い違います。

> **提案**：文言を事実に寄せる。「独自調査銘柄」ではなく
> **「世界オッズ 取得なし（出来高が小さいため）」**のような書き方であれば、
> 数字を出さない方針を保ったまま、出所の誤りも避けられます。

## ❌ N-34（新規）`markets[0]` を代表値にしています

Polymarket の1イベントは複数のサブマーケットを持ちます。
現在のコードは**先頭のサブマーケットだけ**を見ています。

```js
if (ev.markets && ev.markets[0]) { const m = ev.markets[0]; … }
```

実際に API を叩いて確かめました（対照：500イベント取得成功）。

| 銘柄 | サブ数 | `markets[0]` | 表示 | そのイベントの最高値 |
|---|---:|---|---:|---:|
| EWC 2026 CS2部門 優勝チーム予測 | 38 | （先頭候補） | **1%** | **77%** |
| NFL 第61回スーパーボウル 優勝チーム予測 | 33 | （先頭候補） | **1%** | 14% |
| 2026年8月 WTI原油先物価格の到達水準予測 | 26 | （先頭水準） | **1%** | **100%** |
| イングランド・プレミアリーグ 優勝クラブ予測 | 24 | （先頭クラブ） | 50% | 50% |
| Ballon d'Or Winner 2026 | 89 | Mbappé | 7% | Harry Kane **62%** |

**「優勝チーム予測」に「世界の確率 1%」と書いてあります。** 何が1%なのか、読者には分かりません。

```
世界確率が付く44銘柄のうち
  サブマーケットが2件以上（多肢イベント）: 40件
  タイトルが「優勝／受賞者予測」型        :  8件  ← 数字が特定候補のものになる
  markets[0] が 0% で 1% にクランプ      :  9件
```

なお、二者択一の質問では `markets[0]` が正しく対応することもあります。
FRB は `markets[0]` が「50bp以上の利下げ」で、タイトルとも一致していました（0% → クランプで1%）。
**問題は多肢イベントのときだけ**です。

### クランプの副作用

```js
probYes: Math.min(99, Math.max(1, probYes))
```

辞書1000エントリのうち **ちょうど1%が398件（40%）**。
1%群の24時間出来高の中央値は 15,715 で、それ以外（15,000）と変わりません。
**「取引が薄いから1%」ではなく、0%を1%に丸めた結果**が大量に混ざっています。

> **提案**：多肢イベントは「最高値の候補名＋その確率」を出すか、
> そもそも `【世界の確率】` を付けない。0% は 1% に丸めず 0% と出す。

## ❌ Check #14 の穴 — 世界オッズが全滅しても 20/20 PASS

新しい回帰テストはこうです。

```js
if (observedProbs.length >= 20 && distinctProbs.size <= 1) { … FAIL … }
```

**「20件以上あって、値が1種類しかない」**ときだけ落ちます。
つまり**前回と同じ壊れ方（全部50%）**しか見ていません。

### 破壊テスト：オッズ辞書を空にし、Polymarket API を不達にする

プリレンダーは**ビルド時に Polymarket API を直接叩きます**（辞書＋ライブ取得の二段構え）。
そこで両方を止めました。API のホスト名を到達不能なアドレスに差し替えています。

```
オッズ辞書       : 0エントリ
Polymarket API   : 不達
────────────────────────────────
【世界の確率】を持つ銘柄 :   0 / 129
【日本世論調査】        : 129 / 129
自己検証            : 合格 20件 ｜ 不合格 0件   ← PASS
```

**サイトの中心的な比較が全ページから消えても、エンジンは何も言いません。**
`observedProbs.length` が 0 になるので、`>= 20` の前提条件を満たさず、判定に入らないためです。

これは仮定の話ではありません。**プリレンダーはビルド時にネットワークへ出ます。**
Cloudflare のビルドが Polymarket の障害中に走れば、この状態が本番になります。

> **修正案**：件数を「前提条件」ではなく「要件」にする。
> 例：`activeEvents.length >= 40 && observedProbs.length < 20` なら FAIL。
> 併せて、**ライブ取得が0件だったらビルドを失敗させる**（黙って続けない）。

## 所感

**N-30 の直し方は、方向として正しいです。**

```
前 : 値が無い → 50% と書く          （静かに嘘をつく）
後 : 値が無い → 「該当なし」と書く    （無いと言う）
```

第6回で「値が無いときに、それらしい値を出さない」と書いた原則が、そのまま実装されています。
バッジの重なりも二重空白も片づいていて、細部の処理も丁寧でした。

ただ、**同じ原則をあと3か所に適用する必要があります**。

```
OGP・JSON-LD  : 直った       ← 今回
アプリ本体     : 50% のまま    ← N-32（人が見る画面）
出所の表記     : 「独自調査」   ← N-33（無いのは調査ではなくオッズ）
代表値の選び方  : markets[0]   ← N-34（多肢イベントで意味が壊れる）
検査           : 全滅でPASS    ← Check #14
```

とくに **Check #14** は考えさせられました。
前回の症状（全部50%）を検知する形になっていますが、**同じ原因の別の症状（全部消える）は通ります**。
再発防止のテストは、**症状ではなく原因に紐づけないと次を取り逃がす**という例です。
「50%固定でないこと」ではなく「**世界オッズが十分な件数で存在すること**」を要件にすれば、
どちらの症状も同じ1本で止まります。

そして N-34 は、私が第6回で「実オッズを保存すれば直る」と書いたときに
**見落としていた前提**でもあります。「実オッズ」と一言で書きましたが、
1イベントに89件のサブマーケットがある世界では、**どれを実オッズと呼ぶかが設計判断**でした。
そこまで書いていれば、`markets[0]` は選ばれなかったかもしれません。
